Informe de Auditoría y Estado del Proyecto SCI-TSS

Fase: Pre-Producción
Rol del Evaluador: Senior Full Stack Software Engineer
Fecha de Evaluación: 28 de Abril de 2026

1. Resumen Ejecutivo

El proyecto SCI-TSS es una aplicación web transaccional construida con un stack de tecnologías nativas (Vanilla PHP para la API backend, Vanilla JavaScript/HTML/CSS para el frontend, y base de datos relacional). Cuenta con un sistema de autenticación, control de acceso basado en roles (RBAC), gestión de empleados y carga de archivos.

Si bien el proyecto demuestra un avance funcional significativo y un esfuerzo claro por implementar controles de seguridad (CSRF, RBAC, hash de contraseñas), la estructura actual presenta alta deuda técnica, fragmentación de código y riesgos de seguridad críticos derivados de la presencia de scripts de desarrollo y parcheo en el entorno principal. El proyecto NO está listo para producción en su estado actual.

2. Análisis Arquitectónico y Estructural

2.1. Backend (PHP API)

Estado Actual: Se ha optado por una arquitectura sin frameworks (Vanilla PHP). Existe una separación básica usando carpetas /api, pero se observa una grave duplicidad y fragmentación de endpoints (ej. api/employees.php vs api/employees/index.php).

Archivos "Parche": La presencia de archivos como fix_endpoints.php, api/config/config_fixed.php, api/config/cors_fixed.php y api.original.js indica que se han realizado correcciones "en caliente" (hotfixes) para resolver problemas estructurales o de CORS sin refactorizar la raíz del problema.

Riesgo: El mantenimiento a mediano plazo será complejo. La falta de un enrutador (Router) centralizado hace que el flujo de ejecución sea difícil de rastrear.

2.2. Frontend (HTML/JS/CSS)

Estado Actual: Implementación tradicional con múltiples archivos HTML y scripts JS separados (api.js, dashboard.js, rbac.js, etc.).

Puntos Fuertes: Implementación de validaciones (validaciones.js) y manejo de roles en el cliente (rbac.js). Uso de librerías ligeras (qrious.min.js para códigos QR).

Áreas de Mejora: Al no usar un framework reactivo (React, Vue), el manejo del estado del DOM es manual. Se debe garantizar que la API (api.js) centralice correctamente los tokens de sesión y la lógica de reintentos o refresco de tokens si aplica.

3. Auditoría de Seguridad (Vulnerabilidades Críticas)

Esta es el área que requiere intervención inmediata antes de salir a producción.

⚠️ BLOQUEANTE - Scripts de Desarrollo Expuestos: En la raíz del proyecto existen archivos extremadamente peligrosos:

reset_admin.php, reset_default_passwords.php

hash.php, test_hash.php, get_hash.php, hash_result.txt

check_db.php, check_admin.php, db_index_patch.php

Riesgo: Si un atacante descubre estas URLs, podría comprometer la base de datos, resetear contraseñas de administradores o extraer información sensible. Deben ser eliminados o movidos a un entorno aislado offline.

Archivos de Configuración: El archivo .env está en la lista de archivos. Es imperativo asegurar que la configuración del servidor web (Apache/Nginx) bloquee el acceso HTTP directo a archivos .env o .ini.

Carga de Archivos (upload.php y /uploads): Se observan imágenes .jpg subidas. Es vital revisar el código de upload.php para asegurar:

Validación estricta de extensiones y MIME types (no confiar solo en la extensión).

Renombrado seguro de archivos (parece que se usan hashes MD5/SHA, lo cual es correcto: 4af1f04...jpg).

Evitar ejecución de scripts en el directorio /uploads (vía .htaccess o configuración de vhost).

Autenticación y Middlewares: Destaco positivamente la existencia de auth_check.php, RBAC.php y csrf.php. No obstante, el RBAC de frontend debe estar estrictamente respaldado por la validación en el middleware del backend.

4. Base de Datos y Persistencia

Estado Actual: Existe un archivo maestro 01_master_final_spanish.sql y scripts de parcheo (db_index_patch.php).

Deuda Técnica: El proyecto carece de un sistema formal de migraciones (ej. Phinx, Flyway). Depender de parches manuales en PHP para actualizar índices o esquemas en producción es altamente propenso a errores y corrupciones de datos.

5. Infraestructura y Despliegue

Configuración XAMPP (apache-vhost-xampp.conf): XAMPP es un entorno exclusivamente de desarrollo. Bajo ninguna circunstancia debe usarse XAMPP en un entorno de producción. * Recomendación: Se debe desplegar sobre un servidor Linux robusto (Ubuntu/Debian) usando Apache o Nginx de forma nativa, con PHP-FPM, configurando correctamente los permisos de usuario (ej. www-data).

PHP.ini: Se adjunta un php_ini_optimizado.ini. Es una buena práctica, pero debe validarse que variables como display_errors estén en Off, log_errors en On, y expose_php en Off.

6. PLAN DE ACCIÓN Y MEJORAS REQUERIDAS (Roadmap a Producción)

Para llevar este proyecto a nivel de Producción (Senior Standard), confirmo la necesidad de ejecutar los siguientes pasos:

Fase 1: Limpieza y Hardening (Inmediato)

Eliminación de Basura de Desarrollo: Borrar del repositorio y del servidor todos los archivos de test, hashes, reseteo de admins y fixers temporales (reset_admin.php, test_hash.php, fix_endpoints.php, etc.). Si son necesarios, moverlos a un repositorio de "scripts de operaciones" no expuesto a la web.

Consolidación de Archivos Parcheados: Integrar config_fixed.php en el archivo config.php final. Hacer lo mismo con cors_fixed.php. Eliminar los .original. Dejar un código limpio y único.

Asegurar Directorio de Uploads: Crear un .htaccess dentro de la carpeta uploads/ con php_flag engine off o su equivalente, para impedir la ejecución accidental de malware.

Fase 2: Refactorización y Estabilidad

Auditoría de Endpoints: Consolidar la lógica fragmentada. Decidir si la ruta oficial es /api/employees.php o /api/employees/index.php y eliminar las duplicidades.

Revisión del Middleware de Seguridad: Realizar pruebas de penetración (Pen-testing) básicas para validar que un usuario sin privilegios no puede acceder por URL directa a endpoints protegidos, validando que auth_check.php y RBAC.php se inyectan correctamente al inicio de CADA solicitud.

Fase 3: Infraestructura y Pase a Producción

Descartar XAMPP: Configurar un entorno LAMP/LEMP real (Linux, Nginx/Apache, MySQL/PostgreSQL, PHP).

Gestión de Variables de Entorno: Configurar las credenciales reales en el .env del servidor de producción, garantizando que los permisos del archivo sean lectura exclusiva para el usuario del servidor web (ej. chmod 600 .env).

Estrategia de Backup: Implementar un volcado automatizado (cronjob) de la base de datos MySQL antes del lanzamiento.
